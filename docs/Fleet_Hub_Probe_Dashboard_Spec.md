# Fleet Hub · 服务器探针面板升级规格（Codex 实施稿）

> 版本：V1.0 · 2026-10-15  
> 仓库：<https://github.com/witrer/fleet-hub>  
> 视觉基准：本对话最终确认的浅色 Fleet Hub 仪表盘效果图，重点保留 3 列机器卡片、4 个环形仪表、国旗与国家小字、密集的 24 小时延迟条，以及点击仪表盘展开曲线的交互。

## 0. 交付目标与边界

将现有 Fleet Hub WebUI 升级为完整可用的服务器探针总览，不做纯静态样板图；卡片、仪表、历史曲线和延迟条使用后端真实数据，不能展示假数据作为真实数据。保留现有节点注册、SSH/MCP、文件上传、撤销节点、中枢自动更新、认证与状态刷新功能。不要为 UI 改版引入不必要的大型前端框架或破坏现有部署方式。

目前代码可直接复用：
- `app/static/index.html`：无构建依赖的前端，当前为深色主题、3 列节点卡片、线性使用率条，5 秒刷新。
- `app/static/node.py`：探针约每 10 秒上报 CPU、内存、根磁盘使用率、系统运行时间、负载、网络累计收发字节；尚无 GPU 数据。
- `app/app.py`：FastAPI + SQLite，`/api/state` 返回最新节点数据；`/api/nodes/{node_id}/heartbeat` 当前只更新 `nodes.metrics` JSON，没有时序历史。
- `app/test_app.py`、`app/test_node.py`：沿用并扩充现有测试。

## 1. 页面信息架构

采用白色 / 浅灰蓝、克制的高级运维 SaaS 风格，细边框、轻阴影、12–16px 圆角和清晰中文字体；保留品牌 Fleet Hub。优先适配 1440px 以上桌面宽屏，避免不必要的装饰。

1. 顶部：Logo / Fleet Hub；导航“探针面板、节点管理、告警中心、设置”；搜索（主机名、节点 ID、IP 或地区）；状态筛选；网格/列表视图开关；刷新按钮。
2. 概览：在线节点、离线节点、告警节点、总节点数。数字由真实状态计算。
3. 主体：机器卡片响应式网格，宽屏 3 列、中屏 2 列、窄屏 1 列；排序可选名称/在线状态/延迟/资源占用。
4. 原有“接入服务器”“传输任务”“一键上传命令”“中枢更新”功能不可删除；可以整理到折叠区域、导航页签或次级面板，但必须仍可找到并正常使用。
5. 底部：颜色图例、刷新时间、版本及数据时间新鲜度。

### 每台机器卡片（由上到下）

- 头部：机器名（主要文本）、在线/离线/告警状态点、当前延迟（ms）、更多操作菜单。
- 第二行：**国旗 emoji + 中文国家名（11–12px 小字）**，可选城市或地区；附带 IP（可设置隐藏）、系统名称、运行时间。国家识别失败显示“地区未知”，不要猜测。
- 中部：同一水平行四个**圆形进度仪表**：CPU、内存、磁盘、GPU；圆环中心显示百分比，环下显示名称。四个项目必须视觉一致。
- 无 GPU 的节点：GPU 圆环灰化，中心显示“—”，文案“未检测到 GPU”；不能把无 GPU 误报为 0%。缺失数据、离线过期数据均有显式状态。
- 底部：“过去 24 小时延迟”、均值/P95 延迟，并显示**96 根密集的竖直小圆角条**，每根代表 15 分钟；从左到右由旧到新。最下方为“24 小时前”和“现在”。
- 用户点击 CPU/内存/磁盘/GPU 圆环，在该卡片下方展开该指标历史曲线，再次点击收起；切换指标直接替换图表。展开项应记住该节点与所选指标。图表允许 1h、6h、24h 切换；鼠标悬浮显示时间、数值，必要时给出最大/最小/平均。不能把卡片整体点击与危险操作绑定。

## 2. 视觉细节

- 资源环主色：CPU 绿色、内存蓝色、磁盘紫色、GPU 青绿色；负载达到黄色/红色阈值时，改用状态色强调风险。阈值可配置，默认 >=75% 黄色、>=90% 红色。
- 百分比保留整数用于卡片，曲线可保留 1 位小数。CPU/内存/磁盘/GPU 相同字重与中心对齐。
- 延迟条：96 等宽条；建议 CSS Grid `repeat(96, minmax(0, 1fr))`，条间距约 1–2px，高度 13–16px，圆角 2px；小屏仍保留 96 段并降低间距，必要时允许内部横向滚动，不要粗糙合并成少数大块。
- 延迟颜色：绿色=正常，黄色=偏高，红色=超时/严重异常，深灰=明确离线，浅灰=没有观测数据。逐段 Hover/键盘聚焦显示开始与结束时间、样本数、成功率、平均延迟、P95 延迟；屏幕阅读器可读取描述。
- 默认浅色主题，保持较强文本对比度；桌面端卡片信息紧凑但不拥挤，不要让图表默认占据每张卡片空间。
- 按照真实状态决定颜色，示例截图的机器名、位置、IP、数值仅作为视觉参考，不能硬编码进页面。

## 3. 探针采集与数据语义

### 3.1 CPU / 内存 / 磁盘
- 保留现有 10 秒心跳和 CPU/内存/根分区采集。
- 扩展上传原始容量字段，例如 `memory_used_bytes`、`memory_total_bytes`、`disk_used_bytes`、`disk_total_bytes`；页面可展示“已用/总量”。
- 磁盘默认采集 `/`，不要把多个挂载点总空间盲目叠加；未来可以扩展按挂载点列表。
- 新字段可选，老版本探针发送旧负载时仍可被服务端接受。

### 3.2 GPU（可选能力）
- 自动探测 NVIDIA（优先 NVML，可回退 `nvidia-smi`）与 AMD ROCm（按环境选可靠接口或 `rocm-smi`/`amd-smi`）；Hygon DCU 仅在检测到可靠且可验证的本机指标接口时启用，不能伪造或将 CPU 占用当成 GPU 占用。
- 返回结构化 `gpus` 数组：`index`, `vendor`, `name`, `util_percent`, `memory_used_bytes`, `memory_total_bytes`, `temperature_c`（可选）；并提供概览字段 `gpu_percent`。建议概览取有效设备的平均核心占用，并在展开区展示逐卡数据；与单卡 GPU 内存占用相区分。
- 多 GPU 显示 “GPU ×N”，展开曲线可选择单卡或整体；采集失败、无权限、未安装驱动和确实没有 GPU 应当有所区分，至少保证 `null` 不被显示为 0。
- GPU 查询不能阻塞正常心跳：给外部命令设置短超时、容错，并缓存静态设备信息；无 GPU 主机不新增强制依赖。

### 3.3 地区
- 节点可配置 `country_code`（ISO 3166-1 alpha-2）、`country_name`、`region`、`city`；人工配置优先。
- 可选自动识别公网出口 IP 所对应的国家，需缓存结果并允许禁用；这是网络出口的近似位置，不等于物理机房真实位置。**不能根据中枢 IP、SSH 反代端口或 frp 内网地址来推断目标国家**。
- 前端按国家代码生成国旗 emoji，并以小字号显示国家名称；无国家数据则用中性地球图标与“地区未知”。不可把地区信息当身份认证依据。

### 3.4 延迟定义（务必真实可解释）
- V1 的延迟定义为**节点到 Fleet 中枢的 HTTPS 心跳请求往返耗时**，使用 `time.monotonic()` 计时；这是应用层 RTT，不是 ICMP ping，也不一定等于经 frp 转发的 SSH RTT。UI Tooltip/设置说明应标注这一语义。
- 可以将最近一次成功心跳耗时放入下一次心跳的 `latency_ms` 字段，并配套采样时间，避免误认为本次请求尚未完成就测出了 RTT。
- 单次失败请求应记录失败事件，服务器也需要根据心跳断档和代理状态判断离线区间，不能因为探针停止上报而把异常错误地判为 0ms。
- 默认延迟分色阈值：P95 <=100ms 绿色，100–250ms 黄色，>250ms 红色；节点可按地域或业务自定义阈值。网络超时或探测失败优先标记异常；离线和未知数据保持独立语义。

## 4. 24 小时密集延迟条规则

- 24 小时 = **96 个连续、严格按时间排序的 15 分钟桶**；时间以 UTC 进行桶对齐，前端按用户浏览器本地时区格式化 Tooltip。
- 每个桶计算 `sample_count`、`success_count`、`avg_ms`、`p95_ms`，结合可用率与离线记录计算 `status`（`healthy/degraded/critical/offline/unknown`）。不要只用颜色而不保存数据含义。
- `unknown` 用于接入前或没有可信观测的时间，`offline` 用于有足够服务端证据的持续离线；延迟恢复后新桶可重新变绿。
- Hover 既可看到每一根条的具体时间段，也可查看该时间段平均值、P95、成功率和状态原因。
- 最新桶持续增长，数据每 30–60 秒更新即可；节点最新指标继续每 5 秒更新。避免每 5 秒重新拉全量历史。

## 5. 存储与接口

现有 SQLite `nodes.metrics` 仅保存最新 JSON，**不满足历史曲线**。增加轻量时间序列表与必要索引（按 node_id + UTC 分钟桶），建议按分钟聚合上报样本以减少写入量，记录 count、sum、min/max，以及需要计算 P95 的可复现样本或直方图摘要；24h 查询生成 96 个 15 分钟桶。不能从单个平均值再“计算”出伪造的 P95。

建议至少保留 48 小时分钟级样本，定时清理过期记录，并用 SQLite WAL、参数化查询和批量读写减少负担。未来延长保留期时再考虑分层降采样。节点撤销或清除时的数据保留策略应明确定义。

建议新增（路径可以按项目习惯微调）：

- `GET /api/nodes/{id}/history?metric=cpu|memory|disk|gpu&range=1h|6h|24h`：鉴权后返回 `{timestamp,value}` 时序点以及可用的 min/max/avg，缺失时间段返回 `null`；GPU 允许可选设备编号。
- `GET /api/latency/summary?range=24h&bucket=15m`：**一次查询所有可见节点**的 96 桶延迟数据，避免每张卡分别请求造成 N+1 网络和数据库查询。
- `/api/state` 保持旧字段不变，向后兼容地附加 `gpus`、`gpu_percent`、容量、地区、最新延迟与数据新鲜度字段；此接口仍用于最新状态，不直接塞入所有历史点。
- `/api/nodes/{id}/heartbeat` 兼容旧探针负载；对可选字段做类型、范围、数组长度和字符串长度校验；任何新接口沿用管理员 Bearer 鉴权与节点级最小权限。
- 可增加经过身份认证的地区信息更新接口或直接沿用已有配置机制；不要让节点探针任意覆盖人工设置。

## 6. 状态与可用性

- 保持现有在线判定语义：最近心跳 <35 秒 **且** frp SSH 代理在线。将“资源占用超阈值”和“网络延迟异常”标记为 `degraded`，但不要自动将其等同于 SSH 不可达。
- 探针进程断线、GPU 驱动不可用、心跳延迟升高、业务 SSH 隧道断开为不同故障源，展示清晰状态。
- 若浏览器暂时拉不到最新状态，保留上一次数据但显示“数据可能过期”；不得仍以鲜绿色强调“实时”。
- 恢复服务后历史空洞保留为空洞，不插值伪造稳定值；新节点前 24 小时不齐全是正常情况。

## 7. 实施建议与不做的事项

实现顺序：
1. 在 `node.py` 补充容量/GPU/延迟采集，保持旧探针兼容并处理无 GPU。
2. 在 `app.py` 设计数据库迁移、分钟级历史持久化、查询接口和地区数据。
3. 改造 `index.html`：浅色布局、4 环形表、地区国旗、96 个延迟段、可展开曲线、响应式、多状态与真实数据绑定。
4. 补齐 `test_node.py`、`test_app.py` 的定向测试；更新 README 中的监控含义、字段和 API。
5. 保持原有部署/自动更新和全部操作入口可用，不主动改动认证、SSH 或传输系统关键路径。

这次不做：对所有 GPU 驱动的强制安装；另起独立时序数据库；机器学习异常检测；伪造定位；历史数据大量回填；更换整个 Web 框架。

## 8. 验收清单（必须全部可核对）

- [ ] 3 列响应式真实机器卡片，CPU/内存/磁盘/GPU 四环完整；无 GPU 显示“—”而不是 0%。
- [ ] 每台机器头部国旗 + 小字号国家中文名；国家未知状态正确，允许手动纠正。
- [ ] 96 根密集延迟条覆盖 24 小时；绿色/黄/红/离线/未知语义有图例、Tooltip 和键盘可访问性。
- [ ] 点击任一环可展开该指标 1h/6h/24h 曲线，第二次可收起；曲线点来自持久化真实数据。
- [ ] 延迟指标明确是节点到中枢 HTTPS 心跳 RTT；P95 由有效样本计算，断线不显示 0ms。
- [ ] 多 GPU 可分设备查看，缺少驱动或指标的机器仍可正常上报其他指标。
- [ ] 页面最新状态保持 5 秒轮询，历史刷新单独节流；数十节点仍有可接受性能。
- [ ] SQLite 历史数据支持服务重启后保留，按保留期清理，接口鉴权有效。
- [ ] 节点注册、撤销、MCP、SSH、传输任务、上传命令、中枢更新、旧版探针协议仍正常工作。
- [ ] 使用有 GPU、无 GPU、离线、网络延迟高、新注册不足 24 小时等情况验证，补充必要单元和接口测试。
